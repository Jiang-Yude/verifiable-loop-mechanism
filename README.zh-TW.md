# verifiable-loop-mechanism（機器可驗證完成）

English: [README.md](README.md)

一個小而可攜的機制。讓你用 AI agent（Claude Code、Codex 等）跑任務時，「這一輪到底做完了沒」由機器判定，不是由 AI 自己的感覺說了算。

由一個非工程師，為了一人知識庫的日常運作做出來。狀態：草稿、n=1、未經同儕審查。完整論述見 `paper.md`。

## 這個 repo 適合誰

- 你在用 AI agent 跑「有客觀對錯」的任務，希望「做完沒」由機器驗證，不被 AI 唬。
- 你能在終端機跑一行 Python 指令（不必會寫程式，請 AI 幫你跑也可以）。
- 開發者、技術型知識工作者、一人公司都適用，前提是任務本身可以被機器檢查。

## 什麼情況用

適用（有客觀標準、機器檢查得了）：

- 部署前檢查、檔案有沒有放對、看板有沒有讀完整、連結沒壞、測試有沒有過、某段文字出現次數對不對（例如某個函式只能定義一次）。

不適用（沒有客觀標準）：

- 文章寫得好不好、策略對不對、創意品質。這些交給人、或交給另一個 AI 當評審，不要硬套這個機制。

## 用什麼機制

借自 Yuta Tu 的 G-T-W（Grader 打分、Trace 軌跡、Worthy Condition 完成條件）。

- 一支共用的 grader 腳本，讀一份「要檢查哪些項目」的清單（manifest）。
- 跑完吐出一份判決：分數、P0／P1／P2 問題清單、WC（完成條件，等於 P0 數量為 0）。
- 退出碼：0 代表完成條件成立、可宣告做完；2 代表還有 P0、不准宣告做完；1 代表 grader 自己跑不起來。
- 分數只是趨勢參考，不是完成標準。完成與否看 WC。

## 解決什麼問題

三種 AI 常見的「假完成」：

1. 謊報完成：說做好了，其實有可機器檢查的條件還沒過。
2. 繞圈圈停不下來：沒有客觀停止點，一直改、或只修表面的小東西。
3. 規則被忘掉：純文字寫的規則，在記憶（context）壓縮時被丟掉。

核心一句：當一件事有客觀標準，就別讓 AI 用感覺決定它做完了沒，讓一個你能驗證的條件來決定。

## 怎麼跑

```bash
python3 grader/grader.py --root examples --manifest examples/manifest.board.json
```

（manifest 裡的路徑相對 `--root` 解析；內附範例用 `--root examples`。）需要 Python 3.8 以上，只用標準庫、無外部相依。

判決 JSON 範例：

```json
{ "task_id": "...", "score": 100, "wc": true, "p0": [], "p1": [], "p2": [], "checked_at": "..." }
```

- `wc: true`、退出碼 0：完成條件成立，可宣告做完。
- `wc: false`、退出碼 2：還有 P0，不准宣告做完，回去修。
- 退出碼 1：grader 自己跑不起來（例如 manifest 讀不到）。

## 內建檢查

- `file_exists`：檔案在不在。
- `literal_count`：某字串出現剛好幾次（範例：某函式只能出現一次）。
- `min_lines`：檔案沒被截斷到某行數以下（範例：看板沒被截成空檔）。
- `forbid`：某個 regex 不准出現（範例：禁用破折號）。

新檢查就在 `grader/grader.py` 加一個小函式。優先養一個共用函式庫，不要每個任務各寫一支。

## 邊界

只用在有客觀、機器可檢查標準的任務。創意或開放型寫作不要用這個，那些維持人或 LLM 評審。這條邊界是刻意的，目的是擋住驗收機器去污染內容生產。
